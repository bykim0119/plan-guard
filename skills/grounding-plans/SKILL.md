# 설계 결정을 유저와 함께 채워라 (grill)

설계 문서가 통째로 기대는 **핵심 결정**을 AI가 멋대로 정하지 마라. 유저 설계의도와
구현 사이의 갭을 줄이려면, 설계 문서(`specs/`)를 마무리하기 전에 아래 4칸을 유저와
함께 채운다. 검문 훅은 `specs/` 하위 `.md`에만 4칸을 강제한다(`plans/`는 면제).

## 1. 설계 결정 4칸

문서에 `## 설계 결정` 섹션을 만들고, 그 아래 고정 4칸을 둔다. 각 칸은 내용으로
채우거나, 해당 없으면 `N/A: 이유`로 명시한다(빈 칸 금지).

```
## 설계 결정

### 범위
- 만들 것 / 특히 범위 밖(안 만들 것)

### 주춧돌 결정
- 아키텍처·기술스택·데이터 등 틀리면 계획 전체가 무너지는 결정 + 근거

### 핵심 가정·의존
- "이게 사실이라 믿고 계획을 세웠다"는 전제 (검증 안 된 가정이 위험)

### 성공·검증 기준
- "됐다"를 무엇으로 판단하나 (없으면 갭을 잴 자가 없다)
```

추가로 이 계획만의 결정은 `### 자유 결정` 칸에 모은다(고정 4칸이 아닌 것).

## 2. 꼬리표 문법 (한글 글자, 딱 3개만 유효)

「설계 결정」에는 **이미 정해진 것만** 적는다. 세 꼬리표가 빈틈없이 나뉜다.

- `[확인]` — **유저에게 물어 답을 받아** 정한 것.
- `[검증: 근거]` — AI가 파일·문서·실행으로 확인함. **근거 필수**(콜론 뒤 비면 차단).
- `[미정: 이유]` — 결정 사항이지만 지금 일부러 안 정함. **이유 필수**.

`N/A: 이유`(칸 자체가 해당 없음)와 `[미정: 이유]`(결정인데 나중에)는 다르다.
탈출 표기(`[미정]`·`N/A`)는 이유를 같은 줄에 강제해 도장 찍기를 막는다.

```
### 주춧돌 결정
- 벡터DB = Qdrant [검증: 공식문서서 하이브리드 검색 지원 확인]
- 임베딩 모델 [미정: Phase 2 시작 시 30-case smoke로 결정]

### 성공·검증 기준
- 30-case smoke 정확도 ≥ 90% [확인]
```

## 3. 인터뷰 대본 (grill — 한 번에 하나씩)

4칸을 **질문 대본**으로 삼아 유저에게 **한 번에 하나씩** 묻는다. 순서:
범위 → 주춧돌 결정 → 핵심 가정·의존 → 성공·검증 기준.

- **추천답을 곁들여** 묻는다("저라면 X 같은데, 맞아요?"). 유저는 빈 종이에 쓰지
  않고 판단만 하면 되게.
- 답이 모호하거나 큰 결정이면 **가지를 타고 더 캐묻어** 계획별 결정을 자유 결정으로
  발굴한다. 이게 grill의 본업 — 누락된 빈칸을 채우는 일.
- 한 결정이 두 겹이면 갈라 적는다: "X가 Y 되나?"(사실) → `[검증]`,
  "그래서 X 쓸까?"(선택) → 되돌리기 난이도·우선순위에 따라 `[확인]` 또는 `[검증]`.
- 정해진 결정마다 꼬리표를 붙여 문서에 기록한다 → 검문 훅을 통과한다.

## 4. `[확인]` 규율 (훅이 못 잡는 자리)

훅은 글자만 보지 **실제로 유저에게 물었는지는 모른다.** 그러니 규율로 닫는다:

> `[확인]`은 **실제로 유저에게 물어 답을 받은 것에만** 단다.
> AI가 멋대로 정해놓고 `[확인]`을 붙이지 않는다.

아직 안 물어 정해지지 않았으면 그건 결정이 아니므로 `[미정: 이유]`로 적는다.

## 5. 막히면

검문에 막히면 해당 칸을 실제로 채우거나(유저에게 묻거나 AI가 검증), `N/A: 이유` 또는
`[미정: 이유]`로 명시한 뒤 다시 저장한다. 4칸이 과한 가벼운 메모라면 `specs/` 밖에 둔다.

## 6. 지도에서 미검증/미정 노드를 빨갛게 (선택)

구조도 Mermaid에서 `[미정]` 결정을 눈에 띄게 하려면 `classDef undecided fill:#f88;`를
선언하고 해당 노드에 `:::undecided`를 붙인다. 색은 **사람이 보기 위한 표시**일 뿐,
검문 차단은 꼬리표 텍스트로만 판정하므로 색과 무관하다.
