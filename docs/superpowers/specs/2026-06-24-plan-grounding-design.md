# plan-guard 설계 — 계획 근거 검증과 설계 지도

**날짜:** 2026-06-24
**상태:** 설계 승인됨 (구현 계획 대기)
**이번 spec 범위:** 계획 검증 기능 + 구조도(지도) 생성·보기
**다음 spec(범위 밖):** 위치 안내 기능

---

## 1. 목적 (한 줄)

> 설계 지도를 중심으로, **계획의 토대를 검증하고** 구현 중 **내 위치를 안내하는** Claude Code 플러그인.

## 2. 풀려는 문제

사용자가 Claude Code로 작업하며 반복해 겪는 두 가지 불편함. 알고 보면 **한 뿌리**("전체 그림이 눈에 안 보인다")의 두 얼굴이다.

1. **부실한 계획 (토대 문제)** — Claude가 *"이 루트로 가면 이걸 쓸 수 있을 것이다"* 같은 **검증 안 된 가정(주춧돌)** 위에 계획 전체를 쌓는다. 그 주춧돌이 틀리면 부분 수정이 아니라 **계획 전체가 폐기**된다.
2. **위치 상실 (현재 위치 문제)** — Claude가 구현 중 코드 함수 이름·구현 디테일로 설명해서, 설계하는 사람은 *"전체 설계 중 지금 어디인지"* 길을 잃는다. (설명을 만든 Claude는 알지만, 만들지 않은 설계자는 모른다.)

이 둘을 **명시적인 설계 지도 하나**로 동시에 푼다.

## 3. 전체 그림

```
            [ 구조도 = 공유 지도 ]
             /                  \
   계획 검증 기능            위치 안내 기능
 "주춧돌을 실제로 파본다"    "지도 위 지금 여기를 찍는다"
```

- 지도는 두 기능이 **같은 그림을 공유**하게 하는 토대다.
- 해결 자체는 각 기능이 **별도 동작**으로 한다. 지도만 그려선 둘 다 안 풀린다 — 지도를 그려도 주춧돌을 안 파보면 여전히 모래 위에 짓고, 지도가 있어도 위치를 안 찍으면 여전히 헤맨다.
- 두 기능은 의존이 약하다(지도라는 산출물만 공유). 그래서 따로 만든다. 지도를 먼저 만들어야 위치 핀을 꽂을 수 있으므로 **계획 검증 기능을 먼저** 만든다.

## 4. 이번 범위 선긋기

**이번 spec = 계획 검증 기능 + 그것이 만들어내는 구조도**

- ① 계획 짤 때 "주춧돌부터 근거 대라"는 규율 (스킬)
- ② 문서 저장 길목에서 검증 안 된 주춧돌을 막는 검사관 (훅)
- ③ 계획의 구조도를 Mermaid로 그리기 + 브라우저로 보는 명령

**다음 spec(범위 밖) = 위치 안내 기능**

- 구현 중 그 지도 위에 "지금 여기" 핀 꽂기

## 5. 계획 검증 기능

**두 겹 방어**: 애초에 추측을 덜 하게(예방) + 그래도 새어 나가면 막기(검문).

### 5.1 예방 — 계획 짜는 동안 (스킬)

계획을 쓸 때 Claude에 규율을 주입한다:

> 이 계획이 통째로 기대는 **주춧돌 가정**을 따로 짚어라. 각 가정 옆에 **그걸 어떻게 확인했는지 근거**(읽은 파일·실행한 명령·찾은 문서)를 붙여라. 확인 안 한 건 솔직히 `미검증`이라고 표시하라.

계획 문서에 생기는 칸의 예:

```
[주춧돌 가정]
- "auth 모듈이 토큰 갱신을 자체 처리한다"
    근거: src/auth/token.ts:42 직접 확인 ✓
- "X 라이브러리가 스트리밍을 지원한다"
    근거: 미검증 ⚠
```

### 5.2 검문 — 문서 저장 길목 (훅)

문서가 저장될 때 검사관이 주춧돌 칸을 본다. **`미검증` 주춧돌이 있으면 막고**, *"이 가정부터 실제로 확인하고 다시 와"*라고 돌려보낸다.

- **트리거:** superpowers 흐름에서 설계 문서(spec)·계획 문서(plan)가 저장되는 지점.
- **검사 깊이 — 가벼운 방식(채택):** 검사관은 "문서에 **근거가 적혀 있나**"만 본다. 직접 코드를 열어 사실까지 대조하진 않는다.
  - *근거:* 사용자가 겪는 문제의 대부분은 *"아예 안 찾아보고 단정한 것"*이라, 근거 칸이 비었는지만 봐도 거의 다 걸러진다. 매번 코드까지 대조하면 느리고 토큰 비용이 크다(사용자가 토큰에 민감).
  - *한계(감수):* "근거가 있다고 적었지만 실제론 거짓"인 경우는 못 잡는다. 드물고, 핵심 문제는 가벼운 방식으로 충분히 잡힌다.

### 5.3 탈출구 (과잉 차단 방지)

- 일부러 둔 가정이면 `미검증(의도적)`으로 표시하면 검사관이 통과시킨다.
- 막혔을 때 사용자가 "그냥 통과시켜"라고 하면 진행한다.

## 6. 구조도 (지도)

- **형식·위치:** **계획 문서 안에 Mermaid로** 그려 넣는다. 계획과 지도가 한 곳에 있는 "정본".
  - *근거:* 복잡한 프로젝트는 텍스트 트리로 표현 한계가 있고(가지가 옆으로 못 뻗음), Mermaid가 표현력·가독성에서 우위.
- **주춧돌 표시:** 5.1의 주춧돌 가정을 지도 위에서 **색으로** 보여준다. 검증된 주춧돌은 초록, 미검증 주춧돌은 빨강(⚠) — 검사관이 막는 바로 그 지점.
- **전체 보기 (브라우저):** 슬래시 명령(가칭 `/지도`)으로 계획 문서의 Mermaid를 뽑아 HTML 한 장으로 감싸 `explorer.exe`로 Windows 브라우저에 띄운다. 렌더된 그림, 줌 가능, 미검증 주춧돌 강조.

### 6.1 환경 전제 (확인 완료)

- 터미널이 인라인 이미지 프로토콜을 보장하지 않음(`TERM=xterm-256color`, Windows Terminal·kitty·VS Code 아님). → 터미널 칸 안에 그림 직접 표시는 채택하지 않음.
- `node`/`npx`(v20) 사용 가능, `explorer.exe`로 Windows 연동 가능. → 브라우저 렌더 경로는 확실히 동작.

## 7. 구현 때 정할 것 (이 spec에서 미확정)

- **브라우저 렌더 방법:** Mermaid CDN을 부르는 HTML vs `npx`로 그림(PNG/SVG) 굽기 — 가장 가벼운 쪽으로 구현 때 결정.
- **검사관 훅 종류:** `prompt` 훅(작은 모델 판단) 우선 검토 — 가벼운 방식에 부합.
- **슬래시 명령 이름:** `/지도`는 가칭.
- **플러그인 배포 범위:** 우선 본인 로컬 사용. 공유·버전 관리는 추후.

## 8. 비범위 (이번에 하지 않음)

- 위치 안내 기능(구현 중 "지금 여기" 핀) — 다음 spec.
- 검사관이 코드를 직접 열어 사실 대조하는 무거운 검증.
- 터미널 안 이미지 표시(chafa 등).
